## Сценарий записи на звонок

1. Владелец календаря создаёт тип встречи, указывает название, описание и длительность. После сохранения тип появляется в каталоге для гостей.
2. Гость без регистрации выбирает тип встречи в каталоге. Он открывает календарь на ближайшие 14 календарных дней, выбирает день и видит свободное время. Длительность каждого слота совпадает с длительностью выбранного типа встречи.
3. Гость выбирает время, вводит имя и обязательную тему разговора, затем подтверждает запись. Тема после удаления краевых пробелов должна содержать 1–200 Unicode code points; ошибку можно исправить у поля. Если слот ещё свободен, приложение сохраняет встречу и показывает подтверждение с сохранённой сервером темой, датой и временем. Если слот уже заняли, приложение предлагает выбрать другое время. После потери ответа повторная отправка восстанавливает подтверждение без дубля; изменение темы начинает новую попытку.
4. Владелец открывает общий список предстоящих встреч и видит новую запись с типом встречи, полной темой, датой и временем. Для старых записей без темы показывается «Тема не указана».

У приложения один заранее заданный владелец и один календарь для всех типов встреч. Частичное и полное пересечение записей запрещено, в том числе при одновременных запросах. Следующая встреча может начаться в момент окончания предыдущей. В проекте нет авторизации, личных кабинетов и интеграций с внешними календарями.

Для API используем контракт TypeSpec. Из него генерируется OpenAPI, а Hey API создаёт из OpenAPI клиентский SDK и типы маршрутов Fastify. Fastify регистрирует обработчики, которые проверяют входные данные и соблюдают правила бронирования. Приложение собирается в Docker-образ и запускается в контейнере.

Референс Cal.com. [Создание типа встречи](https://cal.com/blog/event-types-guide-calcom) · [Запись гостя](https://cal.com/scheduling) · [Список встреч владельца](https://cal.com/blog/a-complete-walkthrough-of-cal-com-s-booking-dashboard-its-key-features)

## Использование

Запустите сервер из корня проекта.

```bash
mise exec -- npm start
```

Fastify использует порт из переменной окружения `PORT`. По умолчанию это `3000`.

В другом терминале проверьте, что сервер отвечает `200 OK` с телом `{"status":"ok"}`.

```bash
curl --noproxy 127.0.0.1 -i http://127.0.0.1:3000/health
```

Для разработки фронтенда запустите Vite из корня проекта.

```bash
mise exec -- npm run dev
```

Страница откроется по адресу [127.0.0.1:5173](http://127.0.0.1:5173/).

Чтобы создать тип встречи, откройте [страницу владельца](http://127.0.0.1:5173/owner). Сервер сохраняет типы встреч в файле `calendar.sqlite` в рабочем каталоге. Путь к файлу можно задать переменной `CALENDAR_DB_PATH`.

Чтобы открыть каталог с демонстрационным типом встречи, запустите `mise exec -- npm run demo:catalog` вместо `npm start` и перейдите на [страницу записи](http://127.0.0.1:5173/booking). Ответ каталога можно проверить напрямую.

```bash
curl --noproxy 127.0.0.1 --fail-with-body -i http://127.0.0.1:3000/api/meeting-types
```

Для сборки и локального предпросмотра собранной страницы выполните следующие команды.

```bash
mise exec -- npm run build
mise exec -- npm run preview
```

Сборка сохраняется в `frontend/dist`. Предпросмотр доступен по адресу [127.0.0.1:4173](http://127.0.0.1:4173/).

Из корня проекта соберите образ и запустите контейнер. Для этих команд нужен запущенный Docker; установка локальных npm-зависимостей не требуется.

### Railway: опубликованное приложение первого проекта

Этот раздел описывает опубликованное приложение проекта 386 по адресу [call-calendar-386-production-aa4bcc9c.up.railway.app](https://call-calendar-386-production-aa4bcc9c.up.railway.app).

Railway собирает ветку `main` [первого репозитория](https://github.com/shinovnikita/ai-for-developers-project-386) из корневого `Dockerfile` с контекстом `.`. Fastify слушает на `0.0.0.0` и использует порт из переменной `PORT`, которую задаёт Railway. Хостинг проверяет готовность приложения запросом `GET /health`. [Настройка Codex MCP и вход в хостинг](docs/deployment.md)

Типы встреч и записи гостей хранятся в `/app/data/calendar.sqlite` на временном диске контейнера, без постоянного тома. При перезапуске процесса в том же контейнере файл сохраняется. Новый деплой заменяет контейнер, и календарь начинает работу с пустой базой. [Перезапуск и хранение данных на Railway](https://docs.railway.com/deployments/reference#restart)

У сервиса включён режим Serverless. Через 5–10 минут без исходящего трафика сервис засыпает, а первый запрос его будит. В редких случаях для пробуждения Railway пересобирает сервис, поэтому без тома сохранность записей после сна не гарантируется. [Режим Serverless](https://docs.railway.com/deployments/serverless)

### Рабочее расписание

По умолчанию запись доступна по будням с 09:00 до 18:00 по часовому поясу `Europe/Moscow`. Чтобы задать другое расписание, передайте переменную окружения `CALENDAR_SCHEDULE` с JSON-объектом. Ключи от `0` (воскресенье) до `6` (суббота) соответствуют дням недели. Для каждого рабочего дня укажите один или несколько интервалов в формате `ЧЧ:ММ`. Окончание `24:00` обозначает границу дня. Пустой объект `{}` отключает доступность.

```bash
CALENDAR_SCHEDULE='{"1":[{"startsAt":"10:00","endsAt":"17:00"}]}' mise exec -- npm start
```

## Автоматический аудит опубликованного приложения

[Workflow App audit](.github/workflows/app-audit.yml) объединяет ежедневный `schedule` с cron `17 3 * * *` и ручной `workflow_dispatch`. Поле timezone не задано: время запуска — **03:17 UTC / 06:17 Europe/Moscow**. GitHub может [задерживать запуск по расписанию](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule). По умолчанию используется режим `real`; расписание всегда запускает реальный аудит. Ручной запуск разрешён только из `main`: при выборе другой ветки job пропускается, а скрипты повторно проверяют событие и ref перед публикацией.

Цель берётся из repository variable `APP_URL`, уже установленной в `https://call-calendar-386-production-aa4bcc9c.up.railway.app`. Это опубликованное приложение **проекта 386**. Аудит проверяет его HTTP-доступность; наличие новой темы встречи из проекта 387 не проверяется. Полный SHA в отчёте идентифицирует checkout **кода аудита проекта 387**, а не неизвестную этому workflow версию приложения на Railway. Checkout получает точный SHA события с `persist-credentials: false`.

### Что проверяется

[Сборщик](scripts/app-audit-http.mjs) выполняет только `GET /health`, `GET /`, `GET /booking` и `GET /owner`, без авторизации и переходов по redirect. Для `/health` нужны HTTP 200, JSON Content-Type и JSON ровно `{"status":"ok"}`; для страниц — HTTP 200, HTML Content-Type и признаки HTML-документа. На каждый адрес допускаются до трёх попыток по 20 секунд, включая чтение тела, с паузой 5 секунд между неудачными попытками для пробуждения Railway. Успех после повтора считается доступностью; все предыдущие ответы остаются в отчёте.

Сохраняются статусы, Content-Type, Location, длительность, ошибки и фактические тела каждой попытки. Для тела установлен предел **1 MiB**: превышение отмечается ошибкой, сохраняется полученный префикс. Это **HTTP-проверка, а не полноценный браузерный тест интерфейса**: JavaScript, отображение страниц и сценарий записи на встречу здесь не исполняются. Встречи не создаются, данные приложения не меняются. Playwright отдельно проверяет локальное приложение в обычном CI.

### Анализ и публикация находок

[Оркестратор](scripts/app-audit.mjs) использует закреплённый OpenCode **1.19.6**, модель **`openai/gpt-6.1-sol`**, variant **`medium`**, `share: disabled`. Один аудит создаёт одну новую изолированную сессию `opencode run --format json`, без продолжения прошлой сессии, инструментов и интерактивных вопросов. Лимит модели — 8 минут, всего job — 20 минут. Выбор CLI и настройки подтверждены [официальными источниками закреплённой версии](docs/app-audit-opencode-research.md).

Существующий secret `OPENAI_API_KEY` доступен только модельному шагу и передаётся дочернему процессу модели; установка CLI и проверка его версии ключ не получают. Окружение OpenCode собирается по разрешённому списку, без GitHub-токенов и Actions OIDC. Отдельные шаги сбора сведений об issues и публикации используют `GITHUB_TOKEN` через `GH_TOKEN`. Для них заданы `issues: write`, для checkout — `contents: read`; GitHub App, PAT и `id-token: write` этому workflow не нужны.

Агент получает явный prompt, фактический HTTP-отчёт, фрагменты тел ответов до 4096 символов на попытку и сведения о ранее зарегистрированных находках. В фактах кандидата отдельно сохраняется фрагмент до 1024 символов. Содержимое ответов и issues обозначено как данные, а не команды. Агент возвращает JSON вида `{"schemaVersion":1,"summary":"...","findings":[{"id":"http-health-v1","analysis":"..."}]}`. Доверенный код проверяет схему, единственную завершённую сессию и точное совпадение IDs со всеми кандидатами сборщика; агент не может придумать находку или скрыть зафиксированную ошибку. Факты, заголовки и идентификаторы берутся из сборщика, модель добавляет анализ. При отсутствии кандидатов требуется `findings: []`, новые issues не создаются.

[Publisher](scripts/app-audit-issues.mjs) создаёт отдельное issue для каждой новой находки с фактами, APP_URL, полным SHA и ссылкой на Actions run. Устойчивые правила: `http-health-v1`, `http-home-html-v1`, `http-booking-html-v1`, `http-owner-html-v1`. Ключ — SHA-256 от нормализованного APP_URL и ID правила; дата, SHA кода, run ID, HTTP-статус и формулировка агента на него не влияют. В первой строке issue сохраняется маркер `<!-- app-audit:v1:<ключ> -->`.

До анализа и повторно перед публикацией читаются **все страницы REST-списка issues с `state=all`**, по 100 записей, без поискового индекса; PR исключаются. При совпадении маркера открытого **или закрытого** issue publisher записывает его ссылку как `existing`, не создаёт дубль, не переоткрывает issue и не добавляет комментарий. Неполная пагинация завершает аудит ошибкой. POST создания не повторяется автоматически: если ответ потерян после создания, следующий аудит найдёт маркер через REST.

Одна concurrency-группа `app-audit-${{ github.repository }}` общая для обоих событий, `cancel-in-progress: false`. Выполняющийся аудит не отменяется. При [настройке concurrency по умолчанию](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) GitHub сохраняет только один ожидающий запуск: новый ожидающий может заменить предыдущий; это ограничение параллельности, а не очередь с гарантией исполнения каждого запроса.

### Ручной и учебный запуск

После слияния откройте **Actions → App audit → Run workflow**, выберите ветку **main** и `mode=real`. Эквивалент через CLI:

```bash
gh workflow run app-audit.yml --repo shinovnikita/ai-for-developers-project-387 --ref main -f mode=real
```

Режим **`training`** доступен только для ручного `workflow_dispatch`. Он собирает реальные HTTP-наблюдения, но передаёт агенту для публикации одну искусственную находку `training-deduplication-v1`. Эта находка одинакова при каждом учебном запуске и отделена от реальных ошибок HTTP. Учебные отчёт и issue прямо содержат предупреждение: **«УЧЕБНЫЙ ПРИМЕР, не подтверждённый сбой приложения»**. Никакая неисправность опубликованного приложения этим примером не утверждается.

```bash
gh workflow run app-audit.yml --repo shinovnikita/ai-for-developers-project-387 --ref main -f mode=training
```

Дождитесь завершения первого training перед повторением этой же команды. При отсутствии прежнего учебного issue первый запуск должен записать `created`, второй — `existing` со ссылкой на то же issue и тем же ключом. Уже закрытый учебный issue также подавляет создание дубля. Если он существовал до проверки, оба запуска должны показать `existing`.

### Отчёт и хранение результатов

Job Summary показывает итог, режим, APP_URL, полный проверенный SHA, результаты четырёх GET и ссылки на созданные или найденные issues. Ошибки запуска модели, JSONL/JSON, схемы, GitHub API и публикации завершают workflow ошибкой; наличие находки само по себе не является сбоем выполнения аудита.

Artifact `app-audit-<SHA>-<run ID>-<attempt>` хранится **14 дней**. В нём доступны `meta.json`, HTTP-отчёт и тела ответов, `report.json`, `prompt.txt`, фактические `agent.jsonl`, `agent.stderr`, `answer.txt`, `model-version.json`, `model.json`, проверенные `findings.json`, `publication.json`, `outcomes.json`, `report.md` и `errors.json`, если соответствующий этап успел их создать. Запись отчёта, upload и финальный Job Summary выполняются с `always()`, поэтому при ошибке сохраняются уже полученные данные, включая частичную публикацию. Отчёт внутри artifact фиксируется перед загрузкой (`artifacts: pending`); финальный Job Summary после upload учитывает его фактический статус, включая ошибку загрузки. Приватные HOME/config/auth/state сессии не загружаются. Результаты пишутся во временный каталог раннера; локальный `/app-audit-results/` исключён через `.gitignore` и не должен попадать в коммиты.

### Приёмка после merge

До слияния аудит с созданием реальных или учебных issues не запускается. Ссылки на интеграционные прогоны добавляются после фактической проверки; локальные фикстуры не доказывают доступ модели, Railway и право публикации в Actions.

1. После merge зафиксируйте SHA `main`, откройте **Actions → App audit** и запустите `mode=real` командой выше. Дождитесь завершения; проверьте checkout/SHA в `meta.json` и Job Summary, модель/версию, четыре GET и фактические ответы. При отсутствии находок ожидается пустой список issues; при находках — `created` или `existing` с фактами и ссылками.
2. Запустите `mode=training`, дождитесь завершения и сохраните ссылку на учебный issue, его ключ и run. Повторите тот же запуск из `main` и дождитесь завершения. Второй run должен показать `existing` того же issue без дубля, даже если issue уже закрыт. Проверьте учебное предупреждение в обоих отчётах и issue.
3. Убедитесь, что в каждом run доступны artifact и Job Summary. Сверьте `publication.json` с issues, а `answer.txt` — с исходным `agent.jsonl`; не считайте учебную находку реальным сбоем. Не удаляйте маркер при последующем редактировании issue.
4. Для проверки ограничения ветки выберите сохранившуюся PR-ветку в **Run workflow** либо выполните ту же CLI-команду с `--ref <PR-ветка>`: job `audit` должен быть **Skipped**, без модели и публикации. Код ветки должен содержать этот workflow; если ветка удалена, этот контроль пропускается до появления подходящей ветки.
5. После следующего **03:17 UTC / 06:17 Europe/Moscow** проверьте настоящий запуск с событием `schedule`, режимом `real`, SHA `main`, отчётом и artifacts. Допустима задержка GitHub; ручной запуск не является доказательством работы расписания. Сохраните ссылки на реальные runs и учебное issue для приёмки.

## Цикл PR → независимое ревью → исправления

[REVIEW.md](REVIEW.md) задаёт проверяемые критерии, [шаблон PR](.github/pull_request_template.md) — основания, доказательства на SHA, риск и откат. [Описание механизма и контроль после слияния](docs/pr-agent-cycle.md) разделяет локальные фикстуры и реальные интеграционные запуски. [Проверка официальных исходников OpenCode 1.19.6](docs/opencode-review-research.md) объясняет выбор изоляции и OIDC.

- Непривилегированный запрос на `pull_request` запускает независимый reviewer через `workflow_run` из доверенной main; он читает main и снимок проверяемого head без исполнения PR-кода. Каждая сессия новая; модель `openai/gpt-6.1-sol`, variant `medium`.
- `/oc` и `/opencode` от `shinovnikita/User` работают в обсуждении PR и комментариях к diff. Модель готовит предложение; отдельный `candidate-check` выполняет штатную генерацию и `mise run check` в контейнерах без секретов. Publisher проверяет происхождение run/jobs/attempt, GitHub artifact digest и весь кандидат до commit и push в прежнюю ветку. Боты и fork не получают ключ модели.
- Строки `Refs #N` берутся только из единственного блока `<!-- opencode-linked-issues: ["полный URL issue"] -->` в описании PR. Repository и существование каждого issue проверяются через API; обычные упоминания и ссылки не учитываются, дубли удаляются. Пустой/отсутствующий блок не создаёт `Refs #4`.
- Независимый reviewer может читать подходящий PR Release Please; автоматическое исправление `release-please--*` запрещено. Реальную доставку request → worker нужно проверить после merge: при fallback на `GITHUB_TOKEN` request может требовать ручного **Approve workflows to run**.
- Общий лимит — **6 сессий на PR**, включая review и обе команды. До OpenCode доверенный код резервирует запись в ветке `opencode-budget` через GitHub API и fast-forward; SHA, rerun и отмена счётчик не сбрасывают. Отказ — ненулевой статус и артефакт с причиной, SHA и логом.
- Отдельный `browser-evidence` проверяет точный `pull_request.head.sha` без ключа модели: настоящий Fastify, SQLite, Vite, основной и соседние сценарии. Артефакт `browser-pr-<PR>-<SHA>-attempt-<N>` содержит отчёт, HTML/JSON/JUnit, trace, снимки и лог. Хранение — 14 дней; перед merge сохраните нужные доказательства.
- Для main настроены required checks **`check`** (`mise run check`, включая Playwright) и **`browser-evidence`** от GitHub Actions; strict и enforce_admins включены. Ни review, ни Release Please не являются решением о merge.

[Candidate isolation smoke](.github/workflows/candidate-isolation.yml) отдельно проверяет настоящий контейнерный путь генерации и `mise run check` без модели, commit и push. Локально Docker daemon недоступен; фактический результат smoke на head SHA указан в PR. Он не заменяет контроль реальных artifact/job/attempt и App/OIDC-переходов после установки worker в main. При повторе исправления нужен **Re-run all jobs**: повтор только упавших jobs не переиспользует producer предыдущего attempt; новая сессия входит в лимит 6.

До попадания скриптов в доверенную main подготовительный PR не выполнял новую модельную сессию: доверенный `workflow_run` ещё не был установлен в main; дополнительные bootstrap-проверки также явно отмечали пропуск. После слияния нужен контроль по инструкции, а не интерпретация bootstrap как завершённого ревью.

## OpenCode в issues

[Workflow OpenCode](.github/workflows/opencode.yml) вызывает установленный GitHub App **OpenCode Agent** по новому комментарию к обычному issue. Событие — `issue_comment`, только `types: [created]`; доверенный автор — `shinovnikita` с типом аккаунта `User`. Комментарии других пользователей и ботов пропускаются до шага с ключом модели. Команды в PR проходят отдельные jobs `pr-fix` → `candidate-check` → `publish-fix` с общим бюджетом PR, описанным выше.

```text
/oc explain this issue
```

`MENTIONS: /oc,/opencode` разрешает обе команды без учёта регистра. Команда должна быть отдельным словом: перед ней — начало комментария или пробельный символ, после — конец комментария или пробельный символ. `/octopus`, `/oc-extra` и ссылка с `/oc` не запускают агента. Доверенный шаг фильтра читает JSON события через `GITHUB_EVENT_PATH`; текст комментария обрабатывается как данные, без подстановки в shell. GitHub-wrapper передаёт агенту issue и историю комментариев, а `PROMPT` сохраняет текст текущего комментария. Самому модельному агенту читать файл события и внешние служебные файлы раннера не требуется.

CLI закреплён на **OpenCode 1.19.6** и проверяется перед `opencode github run`. Закрепление GitHub action само по себе не фиксировало CLI: прежний action устанавливал последний релиз. Модель — `openai/gpt-6.1-sol`, `VARIANT: medium`, публикация сессии отключена (`SHARE: 'false'`). Repository secret `OPENAI_API_KEY` доступен только шагу **Run OpenCode**.

### Автотриаж новых обращений

[Отдельный workflow OpenCode auto-triage](.github/workflows/opencode-triage.yml) запускается на `issues`, только `types: [opened]`, без `/oc`. Разрешён только репозиторий `shinovnikita/ai-for-developers-project-387` и **автор самого issue** `shinovnikita` с типом `User`. `sender` события не заменяет автора. Боты, другие пользователи и issues с меткой **`ready-for-agent` или `ready-for-human`** пропускаются до checkout, установки CLI и шага с ключом модели. Отфильтрованный job может быть зелёным: у него выполняется только **Check issue eligibility**, остальные шаги имеют статус **Skipped**.

Спецификации и готовые тикеты создавайте **с метками сразу**, например `gh issue create ... --label enhancement --label ready-for-agent`. Для REST передавайте `labels` в исходном POST. Последующее `gh issue edit --add-label` не меняет уже отправленное событие `opened`. Это относится и к агентам `to-spec` / `to-tickets`: правило закреплено в [настройках трекера](docs/agents/issue-tracker.md). Фильтр готовности действует только для автотриажа; ручные `/oc` и `/opencode` работают и в готовых задачах.

Явный `PROMPT` поручает агенту применить `triage`, прочитать инструкции, настройки трекера, глоссарий, ADR и относящуюся к обращению реализацию; проверить существующее поведение и прежние отклонённые запросы. Результат — комментарий с кратким разбором связи запроса с приложением и рекомендацией по категории/состоянию. Если нужны уточнения — один следующий вопрос с рекомендуемым вариантом и причиной. При достаточных сведениях итог может быть без вопроса. Первичный автотриаж только рекомендует метки; дальнейшие действия согласуются в обсуждении. Он не меняет код, метки и состояние issue, не запускает `to-spec`, `to-tickets`, реализацию и не открывает PR. Комментарий публикует wrapper, после чего запуск завершается.

Оба workflow используют ту же модель `openai/gpt-6.1-sol` (`medium`), OpenCode **1.19.6**, `SHARE=false`, GitHub App/OIDC и обёртку `gh`, описанные ниже. Ключ модели доступен только разрешённому шагу **Run OpenCode**. Фильтр читает JSON события как данные; заголовок и тело issue не подставляются в shell, а передаются модельному агенту wrapper-контекстом. Checkout загружает только доверенную `main`, `persist-credentials: false`; PR-ветки с секретами не загружаются.

### Разрешения без ожидания внутри Actions

В прогоне [45044489001](https://github.com/shinovnikita/ai-for-developers-project-387/actions/runs/45044489001) чтение файла события за пределами checkout вызвало `external_directory: ask`; ответа в Actions не было, job завершился по тайм-ауту. Для шага агента задан `OPENCODE_PERMISSION` с `external_directory: deny`: такой доступ возвращает отказ вместо ожидания.

Остальные встроенные источники интерактивности также закрыты: `doom_loop`, `question` и чтение `*.env` / `*.env.*` получают `deny`, с сохранением исключения `*.env.example`. GitHub-wrapper дополнительно запрещает `question` в сессии. Общее автоматическое одобрение не включено. Эти переменные действуют только в Actions; локальные настройки пользователя не меняются.

В 1.19.6 `OPENCODE_PERMISSION` объединяется с конфигурацией после файловых настроек. Правила выбранного агента и сессии могут иметь более высокий приоритет; в текущем checkout нет дополнительных настроек агентов, выбран стандартный `build`. При изменении версии CLI или добавлении настроек агента нужно повторно проверить итоговые правила и отсутствие ожидающих запросов.

### Авторизация gh внутри инструментов

Сохраняется режим **GitHub App/OIDC**: `contents: read` нужен checkout, `id-token: write` — обмену OIDC с audience `opencode-github-action` на временный installation token OpenCode Agent. PAT и передача ограниченного `GITHUB_TOKEN` не нужны; права записи предоставляет установленный App, а не блок `permissions` workflow.

В 1.19.6 wrapper использует токен для Octokit и помещает его в локальный Git `extraheader`, но сам не авторизует `gh`. На свежем раннере одного успешного ответа wrapper недостаточно для работы скиллов `to-spec` / `to-tickets` через `gh`.

Шаг подготовки добавляет в `PATH` обёртку [scripts/opencode-gh.mjs](scripts/opencode-gh.mjs). При каждом вызове `gh` она берёт уже полученный wrapper токен из Git checkout и передаёт его настоящему `gh` через `GH_TOKEN` только в окружении дочернего процесса. Дополнительный обмен OIDC и `gh auth login` не выполняются. Обёртка не выводит токен, не записывает его в отслеживаемые файлы, артефакты или хранилище авторизации `gh` и завершается ошибкой при отсутствии App-токена. `GH_PROMPT_DISABLED=1` исключает интерактивный вход.

Проверка авторизации должна выполняться **из shell-инструмента OpenCode на свежем раннере Actions**. Нужны отдельные проверки чтения issue и комментариев, создания issue, добавления комментария и закрытия тестового issue. Чтение API не подтверждает право записи. Для smoke-проверки используйте одно отдельное issue с префиксом `[OpenCode auth smoke]`, затем закройте его; рабочие issues для проверки записи не меняйте. Локальная авторизация разработчика такой проверкой не считается.

### Интервью и продолжение

Во время интервью агент возвращает краткий разбор и один следующий вопрос с рекомендуемым ответом и обоснованием. Затем запуск завершается, wrapper публикует ответ в issue. Ответьте **новым** комментарием с `/oc`, например:

```text
/oc Выбираю предложенный вариант. Продолжи интервью с учётом этого решения.
```

Редактирование прежнего комментария не запускает workflow. Ограничение одного вопроса действует только для интервью: после согласования решений `to-spec` и `to-tickets` должны выполнять соответствующие скиллы полностью по отдельной ручной команде.

### Границы запуска и проверка после слияния

Checkout всегда берёт доверенную `main` с `persist-credentials: false`. Ветки PR и код из fork не загружаются с ключом модели. Проверка **Verify repository instructions and skills** подтверждает наличие `AGENTS.md`, `docs/agents/*`, скиллов `.agents/skills/`, активного трекера проекта и команды `mise run check`.

Лимит каждого job — **20 минут**. Одна concurrency-группа `opencode-${{ github.repository }}` общая для **ручного workflow и автотриажа**, `cancel-in-progress: false`: одновременно работает максимум один агентный job для репозитория. Выполняющийся job не отменяется; GitHub сохраняет один ожидающий job. Более новый ожидающий job заменяет предыдущий, в том числе из другого workflow. Порядок запуска не гарантирован; это ограничение нагрузки, а не надёжная очередь всех обращений. Неподходящее issue может кратковременно занять место в этой очереди, пока не выполнится фильтр.

Если разбор был вытеснен из ожидания, отменён, завершился ошибкой или был отфильтрован, повторите его новым комментарием от `shinovnikita` в соответствующем issue:

```text
/oc Примени triage к этому обращению с учётом истории. Прочитай AGENTS.md,
docs/agents/*, GLOSSARY.md, ADR и реализацию. Верни краткий разбор,
рекомендацию классификации и при необходимости один следующий вопрос
с рекомендуемым вариантом и причиной. Только обсуждение; заверши запуск.
```

Это ручной повтор, который обходит фильтр готовности. Редактирование, повторное открытие issue и добавление метки не запускают автотриаж. При необходимости можно использовать **Re-run jobs** существующего запуска, но это повтор с исходным событием и его метками, а не новая проверка `opened`.

### Проверка автотриажа после слияния

До слияния `npm run test:workflows` исполняет реальный shell фильтра из нового YAML на безопасных фикстурах: доверенный User без команды, тот же User с каждой из двух готовых меток, бот и недоверенный пользователь. Дополнительно проверяются чужой репозиторий, автор отдельно от `sender`, тип события и shell-синтаксис в тексте. Проверка структуры гарантирует одинаковый фильтр для каждого последующего шага и изоляцию секрета. Вместо модели используется локальная заглушка: для разрешённого случая регистрируется `github run`, для пропущенных вызовов нет. Это **синтетические проверки нового workflow**, не настоящий GitHub `issues.opened` и не проверка ответа модели.

`issues` и `issue_comment` используют workflow из **основной ветки**. Прогон старой `main` не проверяет новый автотриаж. После слияния выполните следующий контроль; тестовые issues заранее не создавайте и #4, #7, #8, #9 для него не меняйте.

1. Дождитесь завершения текущих OpenCode jobs. Войдите в GitHub как **shinovnikita** (обычный аккаунт User). Зафиксируйте SHA merge в `main`. Для каждого теста проверьте SHA workflow в Actions, checkout обновлённой `main`, CLI `1.19.6`, модель и отсутствие ожидающих разрешений. Создавайте issues последовательно, дожидаясь результата первого.
2. Через **Issues → New issue** создайте **без меток готовности и без `/oc`**:

   **Заголовок:** `[Auto-triage smoke] Понятное сообщение, если свободного времени нет`

   **Тело:**
   ```text
   Как гость календаря, хочу понимать, что делать, если у выбранного типа
   встречи нет свободного времени на ближайшие дни. Объясни текущее поведение
   приложения и помоги уточнить ожидаемый результат. Это тест первичного
   автотриажа; пока нужен только разбор, без спецификации, тикетов и кода.
   ```

   Ожидается запуск **OpenCode auto-triage** с событием `issues`, шаг фильтра с `allowed=true`, выполненный **Run OpenCode** и автоматический комментарий с AI-disclaimer, разбором текущего поведения, классификацией и при необходимости одним вопросом с рекомендацией. Новые задачи, PR и изменения кода не появляются. Продолжение проверяется новым комментарием `/oc Продолжи только обсуждение с учётом истории.` — это отдельный запуск ручного **OpenCode**.
3. После завершения первого запуска создайте готовую задачу **с `enhancement` и `ready-for-agent` уже в форме перед Submit new issue**:

   **Заголовок:** `[Auto-triage smoke] Готовая задача — пропустить разбор`

   **Тело:**
   ```text
   Контроль фильтра готовой задачи. Метка ready-for-agent установлена при
   создании. Ожидаемый результат: первичный автотриаж пропущен, модельный
   шаг не выполняется и автоматического комментария нет. Реализацию
   не запускать. Это тестовое обращение, а не задача календаря.
   ```

   Вариант точного создания через `gh` **от своего имени**, после проверки `gh api user --jq .login` → `shinovnikita`:
   ```bash
   gh issue create --repo shinovnikita/ai-for-developers-project-387 \
     --title '[Auto-triage smoke] Готовая задача — пропустить разбор' \
     --body 'Контроль фильтра готовой задачи. Метка ready-for-agent установлена при создании. Ожидаемый результат: первичный автотриаж пропущен, модельный шаг не выполняется и автоматического комментария нет. Реализацию не запускать. Это тестовое обращение, а не задача календаря.' \
     --label enhancement --label ready-for-agent
   ```

## Выпуск версии

При каждом обновлении `main` запускается Release Please. Для ручного запуска откройте **Actions → Release Please → Run workflow** и выберите `main`. [Workflow Release Please](.github/workflows/release-please.yml)

До первого запуска настройте один из способов доступа к GitHub API.

- Для встроенного `GITHUB_TOKEN` включите **Allow GitHub Actions to create and approve pull requests** в **Settings → Actions → General → Workflow permissions**. [Настройки GitHub Actions](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#preventing-github-actions-from-creating-or-approving-pull-requests)
- Чтобы push в ветку release PR запускал проверки CI, добавьте секрет `RELEASE_PLEASE_TOKEN` в **Settings → Secrets and variables → Actions**. Используйте fine-grained personal access token с доступом к этому репозиторию и правом записи в **Contents**, **Issues** и **Pull requests**. [Учётные данные Release Please](https://github.com/googleapis/release-please-action/tree/45996ed1f6d02564a971a2fa1b5860e934307cf7#other-actions-on-release-please-prs)

Workflow выбирает `RELEASE_PLEASE_TOKEN`, если он задан, иначе `github.token`. При подготовке PR список repository secrets успешно проверен: `RELEASE_PLEASE_TOKEN` отсутствует, поэтому сейчас выбран fallback. PAT/App-токен позволяет автоматически доставлять события PR; fallback `GITHUB_TOKEN` не запускает новый push-CI, а PR `opened`/`synchronize`/`reopened` требует **Approve workflows to run**. Наличие разрешённой release-ветки в политике review не доказывает запуск. После установки worker в main проверьте реальное обновление уже открытого PR #13: request, worker, бюджет и полный проверенный SHA; слияние #13 выполняет владелец. [Правила запуска GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)

1. Добавьте в `main` изменение с сообщением по Conventional Commits, например `feat: add a meeting type catalog` или `fix: handle an empty catalog`. При squash merge используйте этот формат в сообщении итогового коммита.
2. Release Please создаст или обновит release PR. Проверьте версию в `package.json` и `package-lock.json` и описание изменений в `CHANGELOG.md`.
3. Объедините release PR с `main`. При следующем запуске Release Please создаст тег версии и GitHub Release.
