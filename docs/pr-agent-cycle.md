# Цикл PR → независимое ревью → исправления

Подготовительный PR создаёт инфраструктуру цикла. Он не реализует тему встречи
из [спецификации #7](https://github.com/shinovnikita/ai-for-developers-project-387/issues/7).
Основания будущей реализации: [обращение #4](https://github.com/shinovnikita/ai-for-developers-project-387/issues/4),
[тикет #8](https://github.com/shinovnikita/ai-for-developers-project-387/issues/8),
затем [тикет #9](https://github.com/shinovnikita/ai-for-developers-project-387/issues/9),
и [финальное согласование человека](https://github.com/shinovnikita/ai-for-developers-project-387/issues/4#issuecomment-7083268893).
Реализация запускается отдельной командой; решение о слиянии принимает владелец.

## Независимая сессия и доверенные данные

Точки входа: [review-request](../.github/workflows/opencode-review-request.yml),
[доверенный review-worker](../.github/workflows/opencode-review.yml),
[inline-request](../.github/workflows/opencode-inline-request.yml) и
[ручной workflow/worker](../.github/workflows/opencode.yml).

```text
PR opened / synchronize / reopened / ready_for_review
  → непривилегированный review-request без ключа модели
  → workflow_run: доверенный review-worker из default main
  → проверка источника request, репозитория, fork, draft и актуального head SHA
  → снимок обсуждения, исходников, diff и CI именно этого SHA
  → атомарное резервирование одного запуска
  → новая сессия OpenCode с REVIEW.md и без инструментов
  → проверка неизменности head SHA
  → COMMENT review с полным SHA и ссылкой на Actions

shinovnikita/User: /oc или /opencode в общем комментарии PR
  → доверенный issue_comment workflow из default main
shinovnikita/User: /oc или /opencode в строке diff
  → непривилегированный inline-request с метаданными комментария
  → workflow_run: доверенный исполнитель из default main
оба пути исправлений
  → те же проверки и общий бюджет PR
  → новая сессия возвращает JSON исправлений
  → неизменяемый артефакт предложения с исходным HEAD
  → candidate-check: изолированные установка/генерация и mise run check
  → полный проверенный кандидат и доказательство происхождения
  → publisher: проверка workflow/job/attempt, артефактов и всех файлов
  → связанные issues → commit → повторная проверка remote HEAD
  → обычный push в прежнюю ветку PR
  → CI, браузерный артефакт и очередное независимое ревью
```

Версия CLI — **OpenCode 1.19.6**, модель — `openai/gpt-6.1-sol`, variant —
`medium`, публикация сессий отключена. У каждой PR-сессии отдельные каталоги
HOME/XDG и новая сессия без resume/continue. Конфигурация, плагины, MCP,
инструкции и зависимости из проверяемого PR не загружаются. Все инструменты
агента запрещены; исходники, обсуждение, ссылки и diff передаются как данные.
Заголовок сессии задан явно; бюджет резервируется до любых возможных
служебных модельных вызовов. Подробности закреплённой версии и официальные
источники: [исследование OpenCode](opencode-review-research.md).

Ревьюер получает доверенный [REVIEW.md](../REVIEW.md), постановку PR,
исходное обращение, спецификацию, тикеты, комментарии с человеческим
согласованием, актуальный diff, снимок исходников и результаты checks/statuses
для полного `pull_request.head.sha`. Недоступный контекст, незавершённый CI,
отсутствующий браузерный артефакт и выход за согласованный объём должны быть
отмечены. Результат содержит только подтверждённые замечания; при их отсутствии
перечисляет проверенное и ограничения. Он не является разрешением на merge.
Если head изменился во время подготовки или перед публикацией, устаревший
результат не публикуется как ревью нового SHA.

Автоматическое ревью ограничено тайм-аутом; устаревшие запуски одного PR
отменяются через отдельную concurrency-группу ревью. У исполнителя другая
группа, поэтому отмена ревью не прерывает исправления. Зарезервированный
бюджет отменённой сессии не возвращается.

Перед резервированием ревью до 12 минут ожидает завершения `check` и
`browser-evidence` именно для проверяемого SHA. Неуспешный CI также передаётся
ревьюеру; ожидание завершения не превращает его в успешный. Если проверки
не завершились вовремя, запуск завершается ошибкой до резерва и модели.
Ревью имеет общий тайм-аут 30 минут, отдельный модельный процесс — 12 минут.
Подготовка исправлений ограничена 25 минутами, проверка кандидата — 45,
публикация — 15 минутами; контейнерные команды имеют свой предел 20 минут.

В подготовительном PR доверенная main ещё не содержит новой инфраструктуры.
Непривилегированные request-workflow могут уже пройти CI, но новый worker на
`workflow_run` до слияния ещё не установлен в default main и может вообще
не запуститься. Если доступный worker обнаружил отсутствие скриптов в main,
шаг `Check installed infrastructure` пропускает модель и сообщает об этом.
Успех request или bootstrap-фильтра не является независимым модельным ревью.
Реальная доставка `workflow_run` и интеграция проверяются после слияния
инфраструктуры владельцем.

## Ручные команды и исправления

Общий комментарий PR приходит в доверенный ручной workflow через
`issue_comment.created`. Для `pull_request_review_comment.created` сначала
работает отдельный непривилегированный inline-request, а затем доверенный
ручной workflow на `workflow_run.completed`. Команды `/oc` и `/opencode`
распознаются без учёта регистра, отдельным словом. `/octopus`, `/oc-extra`
и URL с `/oc` командой не считаются. Доверен автор самого комментария
`shinovnikita` с типом аккаунта `User`; совпадения sender недостаточно.
Боты, включая ответы OpenCode, исправлений не запускают. Секреты не передаются
PR из fork. PR должен быть открыт, находиться в этом репозитории и направляться
в `main`; исходная ветка не может быть `main` или `opencode-budget`. Для
автоматического исправления дополнительно запрещена служебная ветка
`release-please--*`; независимое read-only ревью подходящего release PR разрешено.

YAML workflow из PR также считается недоверенным. Поэтому request-workflow
не получает ключ модели, OIDC или write-токен и не выполняет модельный шаг.
Привилегированный worker берётся только из default main. Для строчного
комментария request передаёт артефакт с фиксированным JSON метаданных
`{commentId, pr, runId, attempt}`. Worker проверяет источник: репозиторий,
путь workflow, тип события, run/attempt, actor `shinovnikita/User` и связь
артефакта с завершившимся request. Из архива читаются только байты ожидаемого
JSON; файлы ZIP не распаковываются в workspace и не исполняются. Метаданные
не заменяют проверку GitHub API: worker заново читает комментарий, проверяет
его реального автора и команду, а репозиторий, ветку и текущий SHA PR получает
из авторитетного ответа API. Поддельный, отсутствующий или несогласованный
request отклоняется до бюджета и модели.

Команды в обычных issues сохраняют прежний GitHub-wrapper и App/OIDC.
Фильтры `ready-for-agent` / `ready-for-human` относятся только к автотриажу
новых issues и не блокируют ручные команды в PR. Бюджет ниже относится к
PR-сессиям, а не к обсуждению в обычных issues.

В PR агент получает общее обсуждение, строчные комментарии, ревью и текущий
комментарий-команду. Исправления возвращаются как JSON с путём файла,
SHA-256 прежнего содержимого и полным новым содержимым. Модель не запускает
shell, git, тесты, `implement-spec` или произвольные скрипты. Job `pr-fix`
проверяет схему, пути, исходные хеши и симлинки, сохраняет неизменяемое
предложение, но ещё не создаёт commit и не получает App/OIDC.

### Проверка окончательного кандидата до commit

Требование AGENTS.md о `mise run check` перед каждым commit сохраняется.
Исправления проходят три jobs одного доверенного workflow: `pr-fix` →
`candidate-check` → `publish-fix` (publisher). Checkout доверенного кода не сохраняет
учётные данные; исходный HEAD PR и SHA доверенного workflow различаются и
фиксируются отдельно.

`candidate-check` получает предложение только от ожидаемого producer этого
run/attempt. Доверенный host-код готовит кандидата, а его код и зависимости
выполняются только в отдельных Docker-контейнерах без ключа модели,
App/OIDC, токенов записи, `.git`, служебных каталогов раннера и Docker socket.
Используется закреплённый по digest образ Playwright. В контейнер доступны
дерево `/work`, отдельный runtime/cache и доверенный read-only файл mise. Read-токен job для загрузки артефакта не
передаётся в контейнер. Код кандидата не исполняется на host раннера.

Сначала непривилегированный bootstrap-контейнер устанавливает зависимости и
выполняет штатную генерацию OpenAPI и SDK. После него host фиксирует полный
кандидат: исходные файлы и результаты `api/generated/`. Другой контейнер
выполняет **`mise run check`**. После завершения host заново читает файлы и
требует точного совпадения с зафиксированными данными; новая генерация внутри
`check` также должна дать тот же результат. Изменение исходников или
сгенерированных данных во время проверки означает отказ. Успешно прошедший
кандидат сохраняется отдельным неизменяемым артефактом.

Publisher не доверяет одному хешу, написанному в JSON артефакта. До получения
App-токена он проверяет через GitHub API происхождение результата: репозиторий,
путь и SHA доверенного workflow, run и его attempt, успешные producer и
`candidate-check` jobs и ожидаемые steps этого attempt. ID артефактов и digest
сопоставляются с outputs ожидаемых jobs, метаданными сервиса GitHub и
фактическими байтами ZIP. Произвольный другой артефакт не заменяет результат
проверки.

Затем publisher независимо восстанавливает ожидаемые исходники из исходного
HEAD и первоначального предложения, сравнивает полный набор файлов, их
содержимое и режимы с проверенным кандидатом и связывает с ним зафиксированные
результаты генерации. Подмена файла, лишний файл, другой кандидат, попытка
повтора артефакта из другого run/attempt или устаревший HEAD приводят к отказу
до commit и push. Привилегированный publisher не устанавливает зависимости и
не запускает код, конфиги, тесты или hooks кандидата.

Только после успешной проверки происхождения и данных publisher получает
App-токен, заново проверяет PR и исходный HEAD, создаёт Conventional Commit и
проверяет целевой репозиторий, прежнюю ветку, родителя commit и remote HEAD
непосредственно перед push. Используется явный `HEAD:refs/heads/<ветка-PR>`,
без force/force-with-lease. Чужой новый commit делает push неуспешным;
перезаписи истории нет. При неуспешном `mise run check` либо несовпадении
доказательств commit и push не выполняются, потраченный резерв не возвращается.

Исполнитель не меняет `.github/`, `.git` и `api/generated/`. Workflow-файлы
OpenCode App публиковать не может; такие исправления выполняет человек через
SSH-доступ. SDK генерируется штатными командами из `api/main.tsp` и входит в
проверяемые данные; сгенерированные файлы не редактируются моделью вручную.
В этом репозитории они исключены из Git, поэтому commit содержит проверенные
исходники, из которых получены проверенные результаты генерации. При неполном
контексте или невозможном изменении агент возвращает объяснение без исправлений.
Если исходный PR принудительно добавил в Git runtime-пути (`node_modules`,
`api/generated`, сборку или отчёты), исправление отклоняется: такие файлы нельзя
исключить из снимка и одновременно считать частью проверенного commit.

### Связанные issues и строки Refs

Единственный источник связей автоматического commit — один явный блок в
описании PR. [Шаблон PR](../.github/pull_request_template.md) содержит пустой
массив; для исправления связанного тикета его заполняют полными URL:

```html
<!-- opencode-linked-issues: ["https://github.com/shinovnikita/ai-for-developers-project-387/issues/8"] -->
```

Publisher заново читает метаданные PR и через API проверяет существование
каждого обычного issue и его принадлежность этому репозиторию. Ссылка на PR,
чужой репозиторий, повреждённый или неоднозначный блок вызывают отказ.
Уникальные номера сортируются; для каждого добавляется отдельная строка
`Refs #N`. Обычные упоминания, closing keywords, обсуждение, текст модели и
контекстные ссылки на #4/#7/#8/#9 не устанавливают связь. Отсутствующий блок
или `[]` дают Conventional Commit без Refs; #4 по умолчанию не добавляется.

### Read-only ревью Release Please и доставка события

Политика чтения допускает release PR этого репозитория в main при соблюдении
обычных проверок состояния, fork, ветки и полного актуального SHA. Политика
исправлений запрещает `release-please--*`, поэтому разрешённое ревью не даёт
агенту права изменять служебную ветку.

Допуск ветки не подтверждает запуск workflow. Действующий
[Release Please](../.github/workflows/release-please.yml) использует
`${{ secrets.RELEASE_PLEASE_TOKEN || github.token }}`. При подготовке PR
`gh secret list` успешно подтвердил отсутствие repository secret
`RELEASE_PLEASE_TOKEN`; текущая конфигурация выбирает `github.token`. Если
позднее настроить отдельный PAT/App-токен, PR-события смогут запускать request
автоматически. В действующем fallback с `GITHUB_TOKEN` события PR `opened`, `synchronize`, `reopened` создают runs,
требующие **Approve workflows to run** от пользователя с write-доступом;
`push`-workflow этим токеном не запускается. Полностью автоматическую доставку
для fallback не обещаем. Основание: [официальные правила GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow).

После установки worker в main нужно дождаться реального обновления открытого
release PR #13 через Release Please либо запустить Release Please для main.
При fallback одобрить ожидающие request-runs. Проверить цепочку
`review-request` → доверенный worker, текущий полный head SHA release PR,
CI/браузерный артефакт, одну запись бюджета и опубликованное read-only ревью.
Проверка функции допуска ветки и фикстуры доставки не заменяют этот контроль.
Автоматическую команду исправления release PR проверяют как отказ до модели;
сам release PR #13 не сливается этой инфраструктурной работой.

## Общий бюджет: шесть сессий на PR

Доверенное хранилище — файл `budget.json` в отдельной ветке
`refs/heads/opencode-budget` репозитория. Его создаёт администратор вне
модельного запуска с начальным содержимым:

```json
{
  "schema": 1,
  "repository": "shinovnikita/ai-for-developers-project-387",
  "reservations": []
}
```

Это служебная ветка состояния, не ветка реализации или источник CI. Не удалять,
не пересоздавать, не обнулять и не редактировать журнал для повторного запуска.
Доступ к записи репозитория и изменению доверенных workflow остаётся
административной границей доверия. Текст PR, комментарии и ответы модели
не являются источником счётчика или лимита.

[opencode-budget.mjs](../scripts/opencode-budget.mjs) напрямую использует
`GITHUB_TOKEN`, переданный как `GH_TOKEN`, до первого вызова модели. Он не
запускает `gh`, GitHub-wrapper или модель ради получения авторизации и не
получает `OPENAI_API_KEY`. Лимит `DEFAULT_LIMIT = 6` задан доверенным кодом.
В одном журнале учитываются автоматические ревью и ручные исправления,
включая команды в строках diff. Одна сессия, вместе с её служебными вызовами,
занимает одну запись.

Атомарное резервирование:

1. Прочитать ref, commit, tree и blob журнала; проверить схему, репозиторий
   и все существующие записи.
2. Посчитать записи данного PR независимо от SHA; при шести отказать.
3. Создать новый tree и commit с единственным родителем — прочитанным commit
   журнала — и добавленной записью.
4. Обновить ref через GitHub Git Database API с `force: false`.
   Два конкурента создают sibling commits; только один может продвинуть ref.
5. При подтверждённом изменении ref перечитать журнал и повторить проверку.
   Число повторов ограничено; при исчерпании повторов модель не запускается.

Запись содержит PR, полный SHA, workflow run ID, run attempt, вид сессии,
время и URL логов. Смена SHA не обнуляет счётчик. Повторный run attempt
для новой сессии требует нового резерва; повторное использование одного
run/attempt/kind отклоняется. **Re-run failed jobs** не позволяет взять
producer/артефакт предыдущего attempt: без успешных producer и проверки в
текущем attempt публикация закрывается отказом. Для новой полной попытки
нужен **Re-run all jobs**, который заново создаёт предложение/сессию и
расходует общий бюджет, если он ещё доступен. После успешного резерва отмена,
ошибка авторизации, модели, проверки кандидата или публикации расходует запуск
консервативно. Возврата записи нет, даже если фактический модельный вызов
не успел состояться. Обычная фильтрация,
недоверенная команда или fork до резервирования бюджет не расходуют.

При 404, 403, повреждении или недоступности состояния запуск закрывается с
ошибкой, без создания пустого журнала и без модели. Отказ сохраняется в JSON
решения, step summary и логах: причина, PR, полный head SHA, URL run и число
известных использованных запусков. `allowed=true` появляется только после
успешной записи. Исчерпание бюджета не публикует успешное ревью; модельный
шаг пропускается, а запуск завершается отказом.

## Ключи и права

`OPENAI_API_KEY` доступен только разрешённому шагу запуска модели. Процесс
OpenCode получает специально собранное окружение без GitHub/App/OIDC-токенов
и без унаследованной конфигурации. Его permission-конфигурация запрещает все
инструменты. Бюджетный фильтр ключа модели не получает.

App-токен для публикации исправлений получается отдельным детерминированным
скриптом: OIDC audience `opencode-github-action` → официальный endpoint
`exchange_github_app_token`. Это тот же обмен, который выполняет wrapper
1.19.6, но без создания сессии или модельного вызова. Git и GitHub API
публикации выполняются только в отдельном publisher после успешной проверки
кандидата и происхождения доказательств, без ключа модели. Существующая обёртка
`scripts/opencode-gh.mjs` для обычных issues продолжает получать App-токен
от GitHub-wrapper. В publisher `GH_TOKEN` остаётся read-токеном GitHub для
проверки provenance, текущего PR и связанных issues; отдельный `APP_TOKEN`
используется только для Git push и итогового комментария. Поэтому установленному
App не требуется `actions: read` для повторной проверки артефактов.
Интерактивных вопросов или ожидания разрешений в Actions нет.

| Job | Права `GITHUB_TOKEN` | Назначение |
| --- | --- | --- |
| Review-request и inline-request | `contents: read` | Передать событие/метаданные непривилегированному request-run; ключа модели, OIDC и write-прав нет. |
| `review` | `contents: write`; `pull-requests: write`; `issues`, `checks`, `statuses`, `actions: read` | Checkout доверенной main, резерв журнала, чтение CI и публикация COMMENT review; OIDC не требуется. |
| `pr-fix` | `contents: write`; `pull-requests`, `issues`, `checks`, `statuses`, `actions: read` | Чтение контекста, резерв журнала, модель и неизменяемое предложение; без App/OIDC и исполнения кандидата. |
| `candidate-check` | `contents`, `actions: read` | Доверенная оркестрация и загрузка предложения; код кандидата выполняется в контейнерах без токенов и секретов. |
| `publish-fix` | `contents`, `pull-requests`, `issues`, `actions: read`; `id-token: write` | Проверка происхождения и полных данных; затем обмен OIDC на App-токен для commit/push и комментария. |
| `opencode` в обычном issue и `triage` | `contents: read`; `id-token: write` | Существующий checkout и GitHub-wrapper с App/OIDC. |
| `check`, `browser-evidence`, `docker-smoke`, `candidate-isolation-smoke` | `contents: read` | Checkout и исполнение обычных проверок без ключа модели и записи в GitHub. |

Уровень workflow по умолчанию не выдаёт дополнительных прав PR-агенту.
Права job не передаются модельному процессу: окружение собирается заново,
а ключ модели существует только в его разрешённом шаге. Публикация review
использует `GITHUB_TOKEN` после модели; в отличие от исправлений, ей не нужен
App-токен для запуска последующего CI.

Ключ модели остаётся repository secret. Редакторы доверенных workflow и
владельцы доступа к настройкам репозитория — административная граница доверия:
такой доступ позволяет изменить workflow и обратиться к repository secrets.
Разделение request/worker защищает от исполнения PR и его YAML доверенным
worker, но не является отдельным ACL уровня environment для секрета.

Обычный `check`, Docker smoke и `browser-evidence` исполняют код и зависимости
PR с `contents: read`, без OIDC, ключа модели и write-прав. Привилегированные
модельный job и publisher получают определение workflow и checkout из
доверенной main; PR для них остаётся данными. Непривилегированный
`candidate-check` исполняет код PR только в описанных выше контейнерах. `pull_request_target` для обхода этой границы не
используется. Детальные права агентных jobs описаны рядом
с `permissions` в workflow; они нужны для чтения контекста, атомарной записи
журнала и отдельной App/OIDC-публикации, а не для исполнения PR.

## Независимый браузерный артефакт

[Browser evidence](../.github/workflows/browser-evidence.yml) запускается
отдельно на каждом PR в main, включая документацию. Checkout использует
`pull_request.head.sha`, а не merge commit `github.sha`; скрипт сравнивает его
с фактическим `git rev-parse HEAD` и сохраняет номер PR, оба полных SHA,
run attempt и ссылку на run в `identity.json`.

Существующие Playwright-сценарии запускают настоящие Fastify, SQLite и Vite:
основной путь «главная → запись → подтверждение → список владельца»,
конфликт записи с выбором смежного слота, потеря настоящего ответа и повтор
после сдвига окна записи. Сценарии темы #7 добавляются с реализацией.

Артефакт `browser-pr-<PR>-<HEAD>-attempt-<N>` содержит Markdown-отчёт с шагами
и наблюдавшимися результатами, JSON, JUnit, HTML, консольный лог и Playwright
trace/screenshots. Загрузка выполняется и при ошибке; `FAIL / INCOMPLETE`
не подтверждает успешный браузерный сценарий. В PR указывается ссылка на
артефакт последнего head SHA. Срок хранения — 14 дней.

## Обязательный CI и доказательства

Стабильные имена checks для PR в main — `check` и `browser-evidence`.
`check` выполняет `mise run check` без path-фильтров, включая PR только с
документацией; команда включает actionlint, проверки инфраструктуры,
генерацию OpenAPI/SDK, lint, типы, Vitest и Playwright. Release Please
работает после merge и не должен быть required check. При подготовке GitHub API
подтвердил защиту main: required checks `check` и `browser-evidence` от GitHub
Actions App `15368`, `strict: true`, `enforce_admins: true`. До настройки защита
и rulesets отсутствовали; существующие дополнительные правила не удалялись.
Ограничение тарифа или недостаток прав не обнаружены. Проверенные ответы API
и head SHA фиксируются в подготовительном PR; перед merge настройку следует
сверить повторно.

Перед ручным merge заново получить `headRefOid` через `gh pr view <PR>` и
проверить `gh pr checks <PR>`, ссылки на Actions и браузерный артефакт.
Обязательные проверки должны быть успешны именно для этого head SHA.
Старый успех, skipped, cancelled или pending достаточным доказательством
не является. Защита CI не заменяет человеческую оценку ревью и риска.
При недоступности настройки отдельно зафиксировать ответ API: отсутствие
прав текущего токена и ограничение тарифа — разные причины.

Локальные и CI-проверки подготовительного PR подтверждают детерминированные
фильтры, схему, конкурентный бюджет, отказ без модели, пути исправлений,
передачу REVIEW.md, фиксацию SHA, порядок «проверка → commit → push»,
отказ при подмене доказательств, Refs, разделение release-политик и настоящий
браузерный путь. Тестовые API,
ответы модельного CLI и выполнение check в тестовом оркестраторе — фикстуры. Они не
подтверждают реальный OIDC-обмен, расход внешнего модельного API, публикацию
ревью или App push. Отдельный [Candidate isolation smoke](../.github/workflows/candidate-isolation.yml)
в текущем PR выполняет настоящий контейнерный путь генерации и `mise run check`
без модели, commit или push и сохраняет receipt и лог. Локально этот Docker-
путь не проверен из-за недоступного Docker daemon; фактический результат CI
и полный SHA фиксируются в описании PR. Сам smoke не исполняет всю
трёхэтапную цепочку исправлений из main: реальные метаданные jobs/attempts,
артефактные переходы, App/OIDC и публикация требуют контроля после merge.

### Отдельная демонстрация исчерпания бюджета

Сейчас дополнительные сессии ради демонстрации не запускаются, учебные issues
или PR не создаются. Позднее владелец выбирает отдельный учебный PR без
продуктовых изменений и проверяет его исходное число резервов в журнале.

1. Учесть автоматическое ревью при открытии как первый запуск. Использовать
   разрешённые общие и строчные команды с безопасным запросом без изменений,
   пока суммарно не появится шесть записей этого PR. Если команда всё же
   изменила код, автоматическое ревью нового commit также входит в шесть;
   считать записи, а не комментарии. Отмена или ошибка после резерва также
   входит в итог.
2. Отправить следующую доверенную команду. Ожидать `budget-exhausted`,
   `allowed=false`, модельный шаг Skipped, неуспешный run и JSON/summary с PR,
   полным SHA и ссылкой на лог. Ревью или исправлений от модели быть не должно.
3. Проверить, что журнал остался с шестью записями, новая смена SHA или rerun
   отказа не обнулили лимит. Не удалять журнал и не увеличивать лимит для
   продолжения демонстрации. Сохранить реальные ссылки и отличить их от фикстур.

## Ограничения и откат

Снимок исходников ограничен 2 MB; бинарные файлы, lockfile, CHANGELOG и каталог
`.agents/` не загружаются в полный исходный снимок. История API имеет ограничение
пагинации. Превышение лимита или недоступный обязательный контекст требуют
человеческой проверки; агент не исполняет код, чтобы добыть недостающие данные.
Реальную доставку `workflow_run` для review-request и inline-request, формат
метаданных GitHub, трёхэтапную проверку кандидата и артефактные переходы нужно
подтвердить контрольными runs после установки worker в default main; фикстуры не доказывают dispatch.
Ответ исправлений ограничен 50 файлами и JSON-схемой, поэтому этот путь
предназначен для конкретных исправлений существующего PR. Отсутствие замечаний
модели не доказывает отсутствие ошибок и не заменяет проверки CI.

Для остановки цикла отключить агентные workflow в Actions, затем отдельным PR
откатить инфраструктурные изменения. Существующие CI и необходимые required
checks сохранять до согласованной замены; не оставлять обязательным check,
который больше не публикуется. Коммиты приложения откатываются обычным revert.
Служебный журнал сохраняется: отключение, откат и повторное включение
инфраструктуры не должны восстанавливать потраченный бюджет.
